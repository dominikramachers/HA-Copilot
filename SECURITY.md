# Sicherheit

## Schwachstellen melden

Bitte melde Sicherheitslücken **nicht** als öffentliches Issue. Nutze stattdessen die private Meldung von GitHub:
**Security → Report a vulnerability** in diesem Repository (Private Vulnerability Reporting). Beschreibe, was du gefunden hast, wie man es nachstellt und welche Version betroffen ist. Zugangsdaten, Tokens und echte Chats gehören nicht in die Meldung.

Ich antworte so schnell wie möglich, in der Regel innerhalb weniger Tage. Das Projekt wird in der Freizeit gepflegt; eine feste Frist kann ich nicht zusagen.

## Unterstützte Versionen

Es gibt Korrekturen nur für die jeweils neueste Version. Bitte vorher aktualisieren.

## Was das Add-on schützt (und was nicht)

- Jede Person sieht nur ihre eigenen Chats, Projekte und das eigene Gedächtnis; die Trennung ist in der Datenbank erzwungen.
- Der Zugang über Home Assistant (Ingress) vertraut nur dem Home-Assistant-Proxy. Der Zugang über eine eigene Domain braucht Anmeldung (Microsoft Entra ID oder Home Assistant) mit serverseitigen Sitzungen.
- Die KI darf in Home Assistant und bei GitHub nur das, was in der Konfiguration freigegeben ist; Änderungen werden im Chat bestätigt, gefährliche Befehle sind gesperrt.
- Linux-Server (ab 0.60.4, nur wenn `servers.enabled` an ist): Der Hub im Add-on nimmt nur TLS-1.3-Verbindungen an; die Agenten verbinden sich ausgehend und werden über ein Zertifikat einer eigenen CA erkannt. Neue Server sind bis zur Bestätigung gesperrt, die KI darf sie über feste, lesende Abfragen ansehen, und jeder Aufruf steht im Protokoll. Geplante Aufgaben dürfen die Server ab 0.62.0 nur über die lesenden Abfragen ansehen (nie ändern, jeder Aufruf mit dem Zusatz „geplante Aufgabe“ im Protokoll); eine geplante Aufgabe mit Websuche kann dennoch Seiten abrufen, die KI hat den Hinweis, nichts von den Servern dorthin weiterzugeben. Auf Servern mit `dnf` (Red Hat, Fedora) gelten dieselben Regeln wie bei apt; da `dnf` auch für die Vorschau root braucht, läuft diese über feste Abfragen des Root-Helfers, und `dnf -y` übernimmt GPG-Schlüssel der eingerichteten Repositories. Änderungen (ab 0.60.7) laufen nur nach Einstufung durch den Agenten und ausdrücklicher Freigabe der Person im Chat (mit dem genauen Befehl; ab 0.64.0 kann die Person „Für <Server> im Chat immer“ wählen: das gilt nur für diesen einen Server, nur in diesem Chat, nur im Arbeitsspeicher, nie für Stufe 3, und jeder Aufruf steht weiter im Protokoll; bis dahin war jede Änderung einzeln freizugeben. Wer Antworten von Servern für nicht vertrauenswürdig hält, wählt nur „Zulassen“: ein Server kann der KI Text unterschieben, und mit der Chat-Freigabe würde ein solcher Befehl auf diesem Server nicht mehr einzeln bestätigt); zerstörerische Befehle (Stufe 3) führt weder der Agent noch der Root-Helfer je aus, und ob ein Server Änderungen erlaubt, steht allein in der lokalen Datei `/etc/copilot-agent/policy`. Port 8101 gehört nur ins Heimnetz oder VPN, nie ins Internet. Ab 0.61.0: Der Agent aktualisiert sich nach lokaler Richtlinie (`update=off|manual|auto`) selbst aus dem Add-on; er prüft Prüfsumme, Größe und einen Probelauf, und mit gesetztem `update_key` auch eine Ed25519-Signatur, und setzt bei einem Fehlstart auf die alte Fassung zurück. **Vertrauensmodell:** ohne `update_key` kann, wer das Add-on kontrolliert, über die Aktualisierung Programme mit den Rechten des Agenten und des Root-Helfers auf die Server bringen; wer das nicht will, setzt `update=off` oder einen `update_key`. Ab 0.61.0 signiert ein GitHub-Workflow die Agenten-Programme beim Veröffentlichen eines Releases (siehe unten „Agenten-Programme signieren“); ist das eingerichtet, trägt das Installationsskript den öffentlichen Schlüssel als `update_key` in die Richtlinie ein, und der Agent nimmt dann nur noch Programme an, die mit dem Schlüssel aus diesem Repository signiert sind. **Automatische Updates (ab 0.68.0):** Der Agent liefert nur Tatsachen; die Regeln liegen im Hub, installiert wird über dieselbe geprüfte Paketaktion wie bei Änderungen durch die KI (Einstufung durch den Agenten, nur Name-Liste mit höchstens 300 Paketen, Stufe 1, Trockenlauf vorab, nie Entfernen). Der Server muss lokal Änderungen erlauben (`ki_access=operate`); mit `auto_update=deny` in `/etc/copilot-agent/policy` lehnt der Agent solche Aufträge dauerhaft ab, weder Hub noch KI können das aufheben. Eingeschaltet wird die Funktion nur mit dem Schalter in der App, die KI im Chat hat dafür weder ein Werkzeug noch Einblick in die Update-Liste (`update_candidates` ist ihr nicht zugänglich). **Vertrauensmodell:** Anders als bei einer einzelnen Freigabe im Chat gibt es hier keine Bestätigung je Lauf: Wer das Add-on (den Hub) kontrolliert, kann auf Servern mit `ki_access=operate` und ohne `auto_update=deny` Paket-Updates der eingerichteten Quellen anstoßen, auch ohne dass die Schalter in der App gedrückt wurden. Pakete kommen nur aus den auf dem Server eingerichteten Quellen und werden auf ihre Signatur geprüft; wer das nicht will, setzt `auto_update=deny`. Automatische Läufe starten nie einen Neustart. Zertifikate der Server erneuern sich selbst (neue Zertifikatsanfrage, der Schlüssel verlässt den Server nicht; das alte Zertifikat gilt höchstens 7 Tage weiter). `file_read` liest jede Datei, die der Agent-Benutzer lesen darf, verweigert aber Pfade, die nach Schlüsseln, Kennwörtern oder Token aussehen, und schwärzt Geheimnisse in der Ausgabe. `server_file_write` schreibt nur in den Ordnern der lokalen Richtlinie (`write_paths`), nur nach Freigabe mit Vergleich und Sicherungskopie, nie in Kontendateien, `sudoers`, `fstab` und SSH-Schlüssel.
- Zugangsdaten (Claude, GitHub, Entra) stehen nur in der Add-on-Konfiguration und werden aus Fehlermeldungen entfernt.
- Der Code wurde vor der Veröffentlichung umfassend geprüft (Stand 0.24.0); Ergebnis und bewusst akzeptierte Restrisiken stehen unter „Sicherheitsprüfung“ in [`copilot/DOCS.md`](copilot/DOCS.md).

**Nicht geschützt:** Ein Add-on mit Zugriff auf Home Assistant ist so sicher wie die Konfiguration, die du einstellst. Gib die Domain-Seite nur frei, wenn du die Hinweise in [`copilot/DOCS.md`](copilot/DOCS.md) gelesen hast, und vergib Schreibrechte sparsam. Inhalte aus dem Web, von GitHub oder aus Anhängen können versuchen, die KI zu beeinflussen („Prompt Injection“); deshalb fragen Änderungen nach solchen Inhalten immer im Chat nach.

## Agenten-Programme signieren (einmalige Einrichtung)

Die Agenten für Linux-Server werden beim Veröffentlichen eines Releases vom Workflow `.github/workflows/release-agent.yml` gebaut und mit einem Ed25519-Schlüssel signiert. Der private Schlüssel liegt nur als GitHub-Secret `AGENT_SIGNING_KEY`, der öffentliche steht in `copilot/agent/update_key.pub` (Base64, 32 Byte). Das Add-on holt beim Bauen die signierten Programme des Releases, prüft sie gegen diesen öffentlichen Schlüssel und liefert sie samt `.sig`-Dateien aus; passt etwas nicht, bleibt es bei den lokal gebauten, unsignierten Programmen (die Seite „Server“ weist darauf hin).

1. Schlüssel erzeugen (auf einem vertrauenswürdigen Rechner): `openssl genpkey -algorithm ed25519 -out agent-signing.pem`
2. Öffentlichen Schlüssel ausgeben: `openssl pkey -in agent-signing.pem -pubout -outform DER | tail -c 32 | base64`. Das Ergebnis (eine Zeile) kommt in die Datei `copilot/agent/update_key.pub` und per Pull Request ins Repository.
3. Privaten Schlüssel eintragen: GitHub → Settings → Secrets and variables → Actions → New repository secret, Name `AGENT_SIGNING_KEY`, Wert ist der **gesamte Inhalt** von `agent-signing.pem`.
4. Die Datei `agent-signing.pem` an einem sicheren Ort sichern (Passwortmanager) und vom Rechner löschen. Nie ins Repository legen.
5. Ablauf je Release: Release veröffentlichen, warten bis der Workflow „Agent signieren“ grün ist (er hängt die Programme, `.sig`-Dateien und `SHA256SUMS` an das Release), **erst danach** das Add-on aktualisieren. Wer früher aktualisiert, bekommt unsignierte Programme; ein Agent mit `update_key` lehnt solche Aktualisierungen ab (sicher, aber ohne Update). Der Workflow lässt sich über „Run workflow“ mit dem Tag nachholen.
6. Bestehende Server bekommen den `update_key` erst, wenn auf ihnen ein frisch erzeugtes Installationsskript läuft (die Richtlinie liegt lokal und wird nie vom Hub geändert). Bereits gesetzte Werte bleiben dabei unverändert.

Geht der private Schlüssel verloren oder wird er bekannt, muss ein neuer erzeugt und auf allen Servern mit `update_key` der Eintrag in `/etc/copilot-agent/policy` ersetzt werden (Skript erneut ausführen reicht nicht, weil vorhandene Werte bleiben).

**Restvertrauen:** Das Installationsskript selbst erzeugt der Hub; wer das Add-on beim ersten Einrichten kontrolliert, könnte dort einen anderen Schlüssel eintragen. Wer das ausschließen will, trägt `update_key` von Hand aus diesem Repository ein.
